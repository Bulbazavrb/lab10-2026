## 2. Пояснення до коду

1. **Серверна частина (`src/app.py`):**
   * `init_db()` — ініціалізує локальну базу даних SQLite `quiz_leaderboard.db` та створює таблицю `scores` для збереження результатів гравців[cite: 36].
   * `@app.route('/')` та `@app.route('/leaderboard')` — рендерять сторінку вікторини та сторінку рейтингу ТОП-15 гравців (відсортовану за спаданням балів і зростанням витраченого часу)[cite: 36, 37].
   * `@app.route('/api/questions/<difficulty>')` — повертає JSON зі списком запитань для обраного рівня складності (`easy`, `medium`, `hard`), попередньо видаляючи поле `answer`, щоб правильні відповіді не можна було підглянути в інспекторі браузера[cite: 36].
   * `@app.route('/api/submit', methods=['POST'])` — приймає JSON із відповідями користувача, перевіряє їх на сервері, записує результат у таблицю `scores` та повертає детальний звіт про кожне питання[cite: 36, 37].
2. **Клієнтська частина (`templates/` та `static/`):**
   * `index.html` та `leaderboard.html` — використовують шаблонізатор **Jinja2** для підключення статичних файлів через `url_for('static', ...)` та виведення таблиці лідерів[cite: 37, 38].
   * `script.js` — керує станами інтерфейсу (налаштування $\rightarrow$ гра $\rightarrow$ результати), запускає таймер `setInterval()`, обробляє вибір варіантів відповідей та відправляє асинхронні запити через `fetch()` без перезавантаження сторінки[cite: 38, 41].
   * `style.css` — забезпечує сучасне оформлення карток, індикатора таймера, підсвічування правильних/неправильних відповідей та таблиці лідерів[cite: 39, 41].

## 3. Контрольні запитання

### Контрольне запитання 1 (з прикладу Flask)
**Запитання:** Як би ви змінили логіку збереження результатів, щоб уникнути проблем з одночасним доступом до текстового файлу при великій кількості користувачів? Запропонуйте альтернативні рішення та обґрунтуйте їх переваги та недоліки[cite: 41].

**Відповідь:**
При одночасному записі у звичайний текстовий файл (`votes.txt`) виникає стан гонитви (*Race Condition*), що призводить до втрати даних або пошкодження JSON-структури. У нашому проєкті цю проблему вирішено переходом на **реляційну базу даних SQLite** (підтримка транзакцій ACID та блокування на рівні БД).

**Альтернативні рішення для високих навантажень:**
1. **Клієнт-серверні реляційні СКБД (PostgreSQL / MySQL):**
   * *Переваги:* повноцінна багатопотоковість, блокування на рівні окремих рядків (Row-level locking), висока надійність та масштабованість.
   * *Недоліки:* потребує встановлення, адміністрування та ресурсів окремого сервера БД.
2. **In-Memory сховища ключ-значення (Redis):**
   * *Переваги:* надшвидка робота в оперативній пам'яті, атомарні операції інкременту (`INCR`) та вбудовані сортовані множини (`Sorted Sets`) для миттєвих таблиць лідерів.
   * *Недоліки:* дані зберігаються в ОЗП, що дорожче за дискове сховище та потребує налаштування персистентності (AOF/RDB).

### Контрольне запитання 2 (до завдання командного проєкту)
**Запитання:** Які альтернативні технології (бібліотеки, фреймворки, підходи) можна було б використати для реалізації вашого проєкту? Опишіть їхні переваги та недоліки порівняно з обраним вами стеком технологій. Як би змінилася архітектура вашого додатку при використанні цих альтернатив[cite: 55]?

**Відповідь:**
1. **Альтернатива 1 — Django + Django REST Framework (DRF):**
   * *Переваги:* вбудована ORM, система міграцій, готова адмін-панель для додавання нових запитань вікторини без редагування коду, вбудований захист від CSRF та система автентифікації користувачів[cite: 43, 53].
   * *Недоліки:* надлишкова структура та більший поріг входу для невеликого проєкту.
   * *Зміна архітектури:* замість одного файлу `app.py` з'явиться чітка структура MVT (`models.py` для моделей `Question` і `Score`, `views.py`, `serializers.py`, `admin.py`).
2. **Альтернатива 2 — FastAPI (Backend) + React / Vue.js (Frontend SPA):**
   * *Переваги:* висока асинхронна продуктивність FastAPI, автоматична генерація документації Swagger UI, валідація даних через Pydantic та реактивний інтерфейс на фронтенді без серверного рендерингу шаблонів.
   * *Недоліки:* ускладнення розробки та розгортання (потрібно підтримувати два окремі проєкти та налаштовувати CORS).
   * *Зміна архітектури:* повне розділення на клієнт і сервер (Headless-архітектура) — сервер віддає виключно JSON, а вся логіка маршрутизації та відображення сторінок переноситься у браузер клієнта.
